POS - Render + PostgreSQL deployment package
============================================

Files
-----
POS.py          Flask application
requirements-postgres.txt  Runtime dependencies (includes Gunicorn and CSRF protection)
render.yaml                Render Blueprint web service configuration
.env.example               Environment-variable template; contains placeholders only

Deploy on Render
----------------
1. Put these files in a private Git repository.
2. Create a PostgreSQL database in Render (or use an existing PostgreSQL service).
3. In Render, choose New > Blueprint and connect the repository, or create a Web Service.
4. If using the Blueprint, set DATABASE_URL, POS_SUPERADMIN_USERNAME, and
   POS_SUPERADMIN_PASSWORD when prompted. POS_SECRET_KEY is generated by Render.
5. Build command: pip install -r requirements-postgres.txt
6. Start command: gunicorn --workers 2 --threads 4 --timeout 120 POS_postgresql:app
7. Set DATABASE_URL to the database's internal connection URL when the app and DB
   are in the same Render region. Do not put credentials in source control.
8. Visit /login and sign in with the configured superadmin credentials.

Security changes in this build
------------------------------
- CSRF protection for POST requests and forms.
- Logout changed to POST (not a state-changing GET request).
- HttpOnly, Secure, SameSite=Lax session cookies; eight-hour permanent session life.
- HTTPS-aware HSTS and additional browser security headers.
- Login-attempt throttling per IP (in-memory, per worker only).
- 10 MB request-body limit.
- Production fails fast if POS_SECRET_KEY is missing.
- Superadmin credentials remain environment-based; password must be at least 12 chars.
- SQL query values remain parameterized in the application.

Important limitations / checklist
--------------------------------
- This package creates/updates PostgreSQL tables but does NOT migrate existing SQLite data.
  Back up and migrate existing POS data before switching a live business over.
- No live PostgreSQL/Render deployment test was possible here. Python syntax was checked;
  test against a staging database before production use.
- Login throttling is per-process and resets on restart. For multiple workers/instances,
  use a shared Redis-backed rate limiter before exposing a high-value deployment publicly.
- Configure PostgreSQL backups, least-privilege DB credentials, and monitoring in Render.
- Use a strong, unique superadmin password and rotate it if it has ever been shared.
- Check all business, billing, report, CSV and PDF flows with test accounts before go-live.
- Do not commit .env files or actual credentials.
